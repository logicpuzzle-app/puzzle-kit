# 盤面IDの契約

決定日: 2026-09-16。新規実装・変更時の設計規則として適用する。
現行コード全体がこの契約を満たしているという宣言ではない。
[既存実装との差分・移行順序](board-id-migration.md)に未対応箇所を記録する。

## 1. IDから期待してよいこと

IDは、盤面上の**同じ要素を参照するための不透明な文字列キー**とする。
採番した値と参照関係を保持する。意味を知るために文字列を解析しない。

| 項目 | 契約 |
| --- | --- |
| 一意性 | 同一盤面の同一種類（cell / vertex / edge）の集合内で一意。Mapのキーと要素の `id` は一致する |
| 同一性 | 同じ盤面・種類で同じIDなら同じ要素。要素の座標や外見が変わっても同一性は維持する |
| 表記 | 保存された文字列の完全一致で比較する。大文字小文字変換・trim・Unicode正規化・数値変換をしない |
| 存在 | IDを持つことは、現在の盤面でその要素が存在・表示・操作可能である保証にはならない。対象のMapと状態を確認する |
| 参照範囲 | 盤面・種類を伴って解決する。他の盤面や別種類の同じ文字列と比較して同一要素とは判断しない |
| 寿命 | 同じ要素が存続する間は維持する。削除したIDを別の要素へ再利用しない。Undoによる同じ要素の復元は再利用に当たらない |
| 保存 | ネイティブ保存・復元はIDと参照関係を保持する。生成器の走査順が同じことに依存しない |
| 不明な参照 | 未解決として扱う。IDの形や近い座標から別要素に黙って付け替えない |

文字列から**座標、種類、隣接、向き、生成順、配列添字、要素数**は推定できない。
連番・欠番なし・接頭辞・区切り文字・長さ・辞書順と空間順の一致も保証しない。
同じ設定で独立に作った2枚の盤面が同じIDになることも保証しない。
UUIDへの統一や既存IDの一括振り直しは、この契約の要件ではない。
採番器は衝突と再利用を防ぎ、利用側は採番方式に依存しない。

表示用の採番、パズルの数字、行列番号はIDと別のデータとして扱う。
画面に番号を出す場合はその用途の値を保持し、ID末尾の数値を流用しない。
表示番号の振り直しによって内部IDを変えてはならない。
例えば、左に列を追加してセルの列番号が変わっても、そのセルのIDとそこを参照する数字・線は維持する。
同じ位置に後から別のセルを作っても、削除済みセルのIDや注記を自動で引き継がせない。

この文書の寿命の規則は盤面のセル・頂点・辺について定める。
数字・線・塗り等の要素自身の `id` も不透明なキーであり、配置先は
`cellId` / `edgeId` / `from` / `to` 等の明示フィールドから読む。
それらのレコードを参照する場合は、盤面に加えてレイヤーと要素の種類も伴わせる。
要素自身のIDと配置先のIDを混同しない。

## 2. 編集とIDの寿命

| 操作 | 必須の振る舞い |
| --- | --- |
| 選択、描画、色・数字の変更、パン・ズーム | 盤面IDと参照関係を変更しない |
| 表示回転、セルサイズ・余白変更、接続を変えない変形 | 存続するセル・頂点・辺のIDを維持し、位置データだけを更新する |
| 行列・余白の追加・削除 | 存続する要素のIDを維持する。新規要素のみ新しいIDを発行する。行列番号が変わってもIDを作り直さない |
| セルの除外 | 残る要素を再採番しない。除外で不要となる頂点・辺の扱いと復元方法を操作側で定義する |
| 一時的な非表示・無効化と解除 | 要素が存続する設計ならIDを保持する。完全削除とは区別する |
| 結合・分割、接続を変える変形 | 消滅する要素と新しく生まれる要素を明示し、新規要素には新IDを発行する。由来は `originalCells` 等のデータで表現する |
| Undo / Redo、試行の取消 | トポロジとそれを参照するデータを一体で復元し、元のIDを復元する |
| ネイティブ保存・読込 | ID・接続・参照関係を復元する。採番器も既存IDや保持する履歴と衝突させない |
| 新規盤面、別盤面への貼付・外部形式の読込 | コピー先での衝突を避け、必要な新IDと対応表を作る。外部形式の番号は内部IDとは別のものとして変換する |

結合・分割での線・塗り・数字の継承には、機能ごとの意味がある。
同じ場所に近いから、あるいは同じ番号だから、という理由では継承しない。
一対多・多対一・削除を区別した対応と継承方針を決め、対応不能なデータは
明示的に削除・保留するか操作を拒否する。データを失う場合は利用者に示し、Undoで戻せるようにする。

旧形式からの移行でIDの変更が必要な場合だけ、明示した対応表による再割当てを許す。
セルだけでなく頂点・辺、両レイヤーの要素、グループ、選択、試行、履歴など
生きている参照全体を同じ処理で更新する。未更新の古い参照を残さない。
移行後の盤面では新しいIDを固定し、以後の編集で繰り返し再採番しない。

保存形式には、削除済みIDを別要素へ再発行しないための情報も必要になる。
連番を使う場合は、現在存在する要素の最大値だけで採番器を復元せず、
過去に発行した上限などを保持する。別方式を使う場合も同じ非再利用の条件を満たす。
Undo後に別の編集へ分岐した場合も、取り消した操作で発行済みのIDを別要素に再発行しない。
履歴で盤面を戻すことと、採番済みの記録を巻き戻すことを混同しない。
読込時は種類ごとの重複ID、Mapキーとidの不一致、解決不能な参照を検査し、
曖昧な上書きで受け入れない。対応不能なら元データを保持して読込・移行を失敗として返す。

## 3. 座標と接続の取得

| 必要な情報 | 取得元 |
| --- | --- |
| セル・頂点・辺 | 対象種類の `topology.cells / vertices / edges.get(id)` |
| 描画位置 | セルの `center`、頂点の `position`、辺の `midpoint` |
| 格子の行列番号 | `topology/queries` の `getCellIndex / getVertexIndex / getEdgeIndex`、または要素の `index` |
| 境界・隣接・辺の両端 | `boundaryVertices`、`boundaryEdges`、`adjacent*`、`startVertex / endVertex` とquery API |
| 従来Grid形式の行列番号 | 明示的にGrid形式を扱うアダプター内の `gridUtils.get*IndexById(id, grid)` |
| 種類・線の対象 | 呼出元の型・選択モード・`TopologyNode.type`・`lineTarget` 等の明示データ |

`index` の順序は **[row, col]**。SVGの **{x, y}** と区別する。
`index` は欠ける・一部がnullになる場合がある。妥当性を確認して使う。
汎用トポロジでの一意性や編集をまたいだ不変性は保証しない。
とくに現行builderの丸めた頂点indexは、非正方形で複数の頂点が同じ値になり得る。
位置・indexをそのまま永続IDの代替キーにしてはならない。

トポロジ内で見つからないIDを、Grid形式として自動再解釈してはならない。
旧データを扱う必要がある場合は、入力形式・バージョンとGrid設定を指定した
互換アダプターで一度変換する。欠損を「隣接している」「検証成功」等に置き換えない。
描画側では未解決の要素を描かない等、操作ごとに失敗時の扱いを定める。

```ts
// セル参照であることは呼出元が決める。IDから種類を推測しない。
const cell = topology.cells.get(cellId);
if (!cell) return null;
return cell.center;

// 禁止: cellId.split('-')、parseInt(cellId.slice(...))、
//       id.startsWith('vertex-') による座標・種類・接続の推測。
```

## 4. IDを生成・解析できる境界

新規コードで形式を知ってよいのは、採番器と明示的な互換・外部形式アダプターだけ。
そこで扱う形式・バージョン・適用盤面を明記する。
採番器が衝突を防ぐために自身の旧IDを読むことと、UIや判定器がIDから位置を読むことは別である。
アダプターも不明な形式を推測で受理せず、未知のIDはそのままのキーとして保持するか変換失敗を返す。

既存の `gridIds.parse*` や `parseLineId` は互換APIであり、汎用の解決APIではない。
新しいUI・ハンドラー・描画・バリデーターから直接使わない。
座標からIDを組み立て直して既存要素を探すことも避け、現在の盤面のlookupを用いる。

IDの完全一致比較、Map/Setのキーとしての利用、ログへの出力は許す。
無向の端点ペアの重複除去では、**順序を揃えるためだけの文字列比較**を許す。
その大小関係に上下左右や進行方向の意味を持たせない。
複合キーは配列・入れ子Map・明確なエンコードを使い、区切り文字を含むIDでも衝突させない。
線の端点は `from/to` 等に保持し、合成した線IDから逆算しない。

## 5. 実装レビューと必要なテスト

盤面・採番・保存・参照処理を変えるPRでは、次を説明する。

- どの要素が存続・追加・削除され、どのIDが維持されるか。
- 座標・接続・種類の情報源と、参照不明時の処理。
- 旧保存データ・Undo/Redo・試行・両レイヤーへの影響と対応表の適用範囲。

テストは採番アルゴリズムのコピーにしない。削ると次の現実的な不具合を
見逃すテストは、重複を統合しつつ残す。

- 同じ形の盤面に、座標と無関係なIDを割り当てても入力・描画・判定先が変わらない。
- 除外・リサイズで残った線や塗りが別の位置に移らず、存続する要素のIDも変わらない。
- 保存・復元とUndo/Redo・試行取消を経てもIDと参照関係が戻り、追加で既存データを上書きしない。
- 消滅した要素や別盤面の参照を、同じ文字列を持つ無関係な要素に付け替えない。
- 要素追加をUndoして別の要素を追加しても、古い参照が新しい要素を指さない。

通常の機能テストは `vertex-2` のような具体的な採番結果に依存しない。
入力fixtureからIDを記録して操作後の同一性を比較する。
採番・同一性に関するテストは残すが、「3番目に生成したから `vertex-2`」という実装の再確認は統合・削除する。
任意IDのfixtureには、区切り文字を含むIDや大小文字だけが違うIDなどを用い、
解析・正規化により参照が壊れる経路を既存の機能テストで検証する。文字列の種類ごとに同じテストを増やさない。
旧形式の読込・バージョン移行を確認するテストでは、実際の保存IDの固定fixtureを使う。
UIに影響する修正にはPlaywright + ChromiumでBefore/Afterの画像・録画を残す。
